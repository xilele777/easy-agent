# 优化与拓展路线

本文把“已观察到的问题”与“有价值但尚未实现的方向”分开。优先级基于当前 Windows 本机调研；动手前应先复现目标问题，并查看[质量与风险评估](../reviews/0000-2026-09-26-评审-质量与风险评估.md)和[测试说明](../../docs/testing.md)。

## 第一阶段：修可靠性与可移植性

进度（2026-09-26）：`Grep` 的 Windows 本机修复及针对性验证已完成，详见[缺陷修复记录](../bugs/0000-2026-09-26-缺陷-Windows下Grep搜索失败.md)。Windows Shell 已明确各入口解释器，Hooks 默认使用 PowerShell、支持显式选壳，`apiKeyHelper` 默认使用 `cmd.exe`，详见[子进程文档](../../docs/subprocesses.md)。测试夹具统一设置 `HOME` 与 `USERPROFILE` 后，`agents`、`stage20`、`stage23` 和配置 smoke 在本机通过。Bash 流式 smoke 明确为 POSIX Shell 测试；Headless 费用字段改为 `null` 表示暂无定价。Unix 环境和完整门禁尚未验证。

## 第二阶段：挑一条产品主线

### A. Windows 优先的 Coding Agent（推荐先做）

**面向谁**：主要在 PowerShell / Windows Terminal 中工作的开发者。**差异化**：原生命令行为、可信提示、文件搜索和会话体验在 Windows 稳定运行，而不是要求额外安装一套 POSIX 环境。

最小可交付范围：

1. `Grep` / Shell / Hooks / apiKeyHelper 的依赖发现与清晰诊断。
2. Windows 下项目路径、符号链接、临时目录和子进程取消的回归套件。
3. 一份可复现的端到端演示：搜索代码 → 生成计划 → 经权限确认修改文件 → 查看 diff/回滚。
4. README 中记录支持矩阵与尚未实现的隔离能力。

**风险**：Shell 与安全沙箱不是一回事。即使命令可以运行，也不能声称已经在 Windows 上隔离执行。

### B. 面向 Pull Request 的结构化代码审查

**面向谁**：需要把 Git diff 变成稳定、可复核审查结果的团队。可复用现有 `-p` Headless、JSON/NDJSON、文件工具与模型协议层，但还要开发审查工作流。

最小可交付范围：

1. 输入：仓库状态、diff、目标分支；限制可读范围与最大上下文。
2. 输出：固定 Schema，包含文件、行号、严重度、证据和建议；解析失败时可恢复。
3. 对比：准备一组带已知缺陷的补丁，统计误报、漏报、耗时和 Token 使用。
4. 安全：默认只读，不执行或安装来自被审查分支的任意脚本。

**风险**：只有“把 diff 传给模型”的包装层，简历价值有限。价值来自证据定位、结构化输出、基准集和误报控制。

### C. 可靠的多 Agent 工作流

**面向谁**：需要并行探索、开发和审查的大型任务。现有 [Agent Teams](../../docs/agent-teams.md) 已支持团队状态、任务认领与消息；可在此基础上研究故障恢复、预算、冲突合并和可视化。

**风险**：状态空间大，涉及后台进程、Worktree、任务所有权和共享文件。建议在熟悉核心循环并完成一条可靠性主线后再做。

## 推荐的四周实施顺序

| 周 | 产出 | 可审查证据 |
| --- | --- | --- |
| 1 | 跑通最小闭环，绘制模块图，复现一个 Windows 失败 | 复现命令、错误输出、调用链笔记 |
| 2 | 修 `Grep` 与相关测试 | 修复前后测试、Windows 和至少一种 Unix 环境结果 |
| 3 | 选择 A 或 B，交付最小工作流 | 真实任务录屏或命令记录、输入输出样例 |
| 4 | 加基准任务与文档，整理简历描述 | 成功率/误报/耗时等可解释指标，明确已知限制 |

## 写简历时怎么描述

保留上游 [MIT License](../../LICENSE) 与原作者署名，写“基于 Easy Agent 二次开发”。描述重点放在**你负责的模块、解决的具体故障、验证方法与量化结果**。在没有跑过真实模型任务和跨平台测试之前，不要写“支持所有模型”“生产级沙箱”或“零故障跨平台”。
