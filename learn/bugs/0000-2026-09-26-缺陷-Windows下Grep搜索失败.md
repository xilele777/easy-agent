# Windows 下 Grep 搜索失败

> 状态：Windows 本机已修复并验证；Unix 环境尚未验证。记录于 2026-09-26，原始基线提交 `56c2cdc`。

## 现象

本机已能找到 `rg.exe`，但运行 `npm run verify:production` 时，`path-boundary` 测试中的“普通工作区文件应能被 Grep 搜索”断言失败，返回 `Error running grep search: spawn grep ENOENT`。其余路径边界断言的结果不能据此推断为失败。

## 环境与复现

环境为 Windows / PowerShell、Node.js 24.14.0。本机 `Get-Command rg` 返回可执行文件路径，`Get-Command sh` 和 `Get-Command grep` 找不到命令。

```powershell
Get-Command rg
Get-Command sh -ErrorAction SilentlyContinue
Get-Command grep -ErrorAction SilentlyContinue
npm run test:path-boundary
```

预期：`Grep` 使用可用的 `rg`，能在普通工作区文件中返回匹配内容。

实际：`Grep` 转而启动缺失的 `grep`，产生 `ENOENT`。

## 原因定位

[`grepTool.ts`](../../src/tools/grepTool.ts) 的 `hasCommand("rg")` 通过 `sh -lc "command -v rg"` 探测。Windows 没有 `sh` 时，异常被捕获并返回 `false`，即使 `rg.exe` 已在 `PATH` 上。工具于是走到 `grep` 回退分支，最终启动失败。

这是“依赖探测错误”引起的功能故障；[工作区路径验证](../../src/tools/pathUtils.ts)仍需要保留，修复时不能绕过它。

## 建议修复与验收

1. 用不依赖 `sh` 的方式探测或直接尝试启动 `rg`；只有确认不可用时才考虑回退。
2. `rg` 和 `grep` 都不可用时，返回清楚的安装或配置提示。
3. 覆盖“有 `rg`、无 `sh`”“只有 `grep`”“两者都没有”的行为，并重跑 [路径边界测试](../../src/scripts/test-path-boundary.ts)。
4. 确认符号链接越界仍被拒绝，普通目录和文件搜索仍成功。

这个记录只针对已定位的 `Grep` 问题；其他失败项及其证据见[质量与风险评估](../reviews/0000-2026-09-26-评审-质量与风险评估.md)。

## 修复记录（2026-09-26）

`Grep` 现在直接启动 `rg`，仅在启动返回 `ENOENT` 时回退到 `grep`；两者都不存在时提示安装 ripgrep 或将 grep 加入 `PATH`。搜索仍通过原有的 `withValidatedWorkspacePath` 进行路径校验。`grep` 回退使用 `-r`，避免递归跟随目录内的符号链接；调用参数使用 `--` 分隔模式和选项，避免以 `-` 开头的模式被当成命令选项。

修复前，`npm run test:path-boundary` 的普通搜索断言因 `spawn grep ENOENT` 失败。修复后，本机运行 `npm run test:grep-command`、`npm run test:path-boundary`、`npm run typecheck` 均通过。命令用例覆盖只有 `rg`、只有 `grep`、两者都缺失及 `rg` 自身报错；路径测试确认普通目录与文件搜索、直接越界链接拒绝，以及搜索时不跟随嵌套越界链接。尚未取得 Unix 环境的运行结果。
