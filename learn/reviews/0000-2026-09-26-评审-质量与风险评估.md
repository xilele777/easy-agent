# 质量与风险评估

> 基线时间：2026-09-26；本机 Windows / PowerShell，Node.js 24.14.0；仓库提交 `56c2cdc`。这是一次本地评估，不代表 macOS、Linux 或在线模型服务的运行结果。

## 已执行的验证

执行 `npm ci --ignore-scripts --no-audit --no-fund` 后，运行 `npm run verify:production`：**TypeScript 类型检查通过、tsup 打包通过；57 项离线检查中 50 项通过、7 项失败，命令退出码为 1**。另运行 `node dist/eagent.js --help` 和 `--version`，两者正常；构建产物显示版本 `0.1.1`。

七个失败项分别是 `path-boundary`、`agents`、`background-worktree`、`hooks`、`styles-commands`、`configuration`、`bash-stream`。这里没有运行 `platform` 宿主沙箱测试或 `live` 真实模型测试。完整测试分组见[仓库测试说明](../../docs/testing.md)和[测试清单](../../scripts/verify-production.ts)。

## 已定位的现象

| 现象 | 证据与判断 | 下一步验证 |
| --- | --- | --- |
| Windows 上普通 `Grep` 搜索失败 | [`grepTool.ts`](../../src/tools/grepTool.ts) 用 `sh -lc "command -v rg"` 探测 `rg`。本机 `rg.exe` 存在，但没有 `sh`，于是误判并回退到不存在的 `grep`；`path-boundary` 的正常搜索断言得到 `spawn grep ENOENT`。这是可复现的产品兼容问题。 | 不依赖 `sh` 探测可执行文件，并在“只有 rg”“只有 grep”“两者皆无”环境测试。 |
| Agent 测试清理失败 | `agents` 运行到权限检查后，临时目录删除报 `EBUSY`；测试的 [清理代码](../../src/scripts/test-agents.ts) 没有对 Windows 文件占用做重试。具体是谁持有句柄仍需调查。 | 单独重复该测试，记录残留进程/文件句柄；修复根因后再考虑删除重试。 |
| Worktree 测试有路径断言失败 | `background-worktree` 的两个断言预期修改 `HOME` 后路径随之改变；实现中的 [`paths.ts`](../../src/utils/paths.ts) 明确使用 `os.homedir()`。Windows 下更依赖 `USERPROFILE`，所以这是测试夹具与路径约定不一致的强线索，不能直接判定业务路径错误。 | 让测试通过隔离环境注入 home，分别在 Windows 与 Unix 验证。 |
| Hooks / 配置测试在本机失败 | [Hook 执行器](../../src/hooks/executor.ts) 明确运行 `bash` 或 `sh`；[apiKeyHelper](../../src/services/api/apiKeyHelper.ts) 默认 `/bin/bash`。本机没有 `sh`；`bash` 命中 WindowsApps 启动程序，但 `bash --version` 退出码为 1 并报告 WSL 访问失败。因此当前环境无法正常运行这些 POSIX 命令。`hooks` 还存在用户配置路径断言失败，需逐项复核。 | 明确 Windows 所需 shell，或实现可配置的原生命令执行方式；对每个失败断言单独确认原因。 |
| 输出样式测试失败 | `styles-commands` 的持久化样式断言失败，随后临时目录清理出现 `EBUSY`。目前只确认现象，尚未确定逻辑故障或测试环境因素。 | 独立运行、检查用户目录隔离与句柄；别把两个现象合并成一个根因。 |
| Bash 流式 smoke 失败 | `bash-stream` 收到增量快照，但最终缺少预期的 `line5`，工具结果也标记失败。该测试使用 POSIX Shell 循环命令，当前证据不足以判断是 Shell、进程结束还是流式收集问题。 | 保留命令 stderr、exit code 和最后一帧，单独定位。 |

## 做得好的地方

- **测试门禁确实覆盖多个层面**：CLI/Headless、Provider 流、工具、安全、MCP、Skills、插件、Ink 界面均在离线验证中有脚本；CI 在 Linux 上运行完整默认门禁，并在 macOS、Windows 上运行核心组。参见 [CI 配置](../../.github/workflows/ci.yml) 与 [测试说明](../../docs/testing.md)。
- **核心职责有边界**：`QueryEngine`、Agent 循环、工具注册和 Provider 适配可分别定位，便于先理解最小闭环。
- **安全决策有专门实现和回归项**：项目可信判断、Allow/Ask/Deny、真实路径边界、会话私有数据、受控子进程和宿主沙箱都有对应代码与[安全文档](../../docs/configuration-security.md)。
- **发布流程可复现**：`package.json` 定义类型检查、打包和发布前门禁；`dist/` 由 tsup 生成，不需要手工维护。

## 局限与技术债

1. **Windows 可移植性不完整**。项目有原生 [PowerShell 工具](../../src/tools/powerShellTool.ts)，但 `Grep` 探测、Hooks、apiKeyHelper 与部分测试仍有 POSIX Shell 假设。[沙箱文档](../../docs/sandbox-security.md)明确 Windows 宿主沙箱尚未集成：启用 failClosed 时会阻止 PowerShell，而不是提供隔离。
2. **默认门禁不证明真实 API 可用**。`live` 组需凭证和网络，默认不执行。模型服务的工具调用、配额、流中断与实际模型权限仍需专门验证。
3. **代码体量与集中度较高**。`QueryEngine`、`agenticLoop`、`useAgentSession` 均是千行级热点。改动一个事件或权限路径时容易影响多个消费者；需要以行为测试约束拆分，而不是为了拆文件而拆。
4. **静态质量工具不齐**。有 `strict` TypeScript，但 `package.json` 没有统一 `lint`/`format` 脚本，也没有通用 `npm test`；现有测试以 smoke 和 characterization 脚本为主。引入规则前应先固定基线，避免一次性格式化掩盖功能改动。
5. **费用字段尚未实现**。[Headless 输出](../../src/entrypoint/headless.ts)的 `total_cost_usd` 目前固定为 0，不能用于账单或成本优化结论。

## 评估结论

它是**学习 Agent 系统和二次开发的较好基础**：模块完整、文档丰富、离线测试多。把它作为生产级、跨平台、安全隔离完善的工具还需要额外验证与修复。若用于简历，最有说服力的材料是：明确的问题复现、改动前后行为、跨平台测试，以及真实使用场景；不要只罗列上游已有功能。

## 实施进度更新（2026-09-26）

上述 57 项门禁结果保留为原始基线。本机后续针对性验证中，`Grep` 的普通搜索与路径边界、`agents`、`stage20`、`stage23`、配置 smoke、Windows 原生 Shell 用例、Headless 特征测试以及类型检查均通过。`Grep` 修复见[缺陷记录](../bugs/0000-2026-09-26-缺陷-Windows下Grep搜索失败.md)。

`agents` 的断言完成后临时目录删除遇到 `EBUSY`，在没有该测试段子进程的情况下，为删除加了有限重试；若持续失败，原始异常仍会报告。`stage20` 和 `stage23` 的失败来自仅设置 `HOME`，而 Windows 路径工具使用 `os.homedir()`，测试现同时设置 `USERPROFILE`。配置 smoke 中的 helper 失败来自 Windows 默认执行 `/bin/bash`，现默认使用 `ComSpec` / `cmd.exe`。

原 Stage 22 Hooks 与 Bash 流式测试使用 POSIX 语法，现于门禁中明确限定 macOS/Linux；Windows 门禁另有原生 PowerShell、Hooks、helper 与缺失解释器诊断用例。这不等于 Windows 已支持 Bash 或宿主沙箱。Headless 的 `total_cost_usd` 现为 `null`，表示尚无定价来源。尚未重跑完整门禁，也没有 Unix 环境或真实模型结果。
